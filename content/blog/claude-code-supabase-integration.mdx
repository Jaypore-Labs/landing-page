This is part 7 of the AI-tools-for-engineers series. Parts 5 and 6 covered MCP fundamentals and patterns. This article is the full setup guide for connecting Claude Code to Supabase through Supabase's official MCP server: the exact commands, the config file, how to lock it down, how to check it works, and what to do when it doesn't.

By the end you'll have Claude Code (the same server works with Codex) querying a Supabase project in read-only mode, with a clear path to allowing writes on a development project when you're ready.

## Quick setup

The short version, verified against [Supabase's MCP docs](https://supabase.com/docs/guides/getting-started/mcp) and [Claude Code's MCP docs](https://code.claude.com/docs/en/mcp):

```bash
# 1. Add the hosted Supabase MCP server, shared with the team via .mcp.json
claude mcp add --scope project --transport http supabase "https://mcp.supabase.com/mcp"

# 2. Start Claude Code and sign in to Supabase in the browser
claude
/mcp

# 3. Check the connection
claude mcp list
```

The safer version, which we recommend for anything other than a throwaway project, pins the server to one project and makes it read-only:

```bash
claude mcp add --scope project --transport http supabase \
  "https://mcp.supabase.com/mcp?project_ref=YOUR_PROJECT_REF&read_only=true"
```

Replace `YOUR_PROJECT_REF` with the reference ID from your project's URL in the Supabase dashboard. Quote the URL, because the `&` will otherwise be read by your shell.

## What you'll have at the end

- Claude Code connected to the official Supabase MCP server over HTTP.
- OAuth sign-in, so there's no access token sitting in a config file.
- The server scoped to one project and restricted to read-only SQL.
- A `.mcp.json` the rest of the team can use.
- A tested path for migrations that keeps a human on the final command.

## Prerequisites

- A Supabase project. Use a development or staging project for the first weeks, not production.
- Claude Code installed and logged in. If you haven't done that, start with [how to install Claude Code](/blog/how-to-install-claude-code).
- A browser on the same machine for the OAuth step.
- Optional: the Supabase CLI, for local development and for running migrations yourself.

## Step 1: add the Supabase MCP server to Claude Code

Supabase hosts its MCP server at `https://mcp.supabase.com/mcp`. Claude Code connects to remote servers with the HTTP transport:

```bash
claude mcp add --scope project --transport http supabase "https://mcp.supabase.com/mcp"
```

What each part does:

- `--transport http` tells Claude Code this is a remote server, not a local process.
- `--scope project` writes the entry to `.mcp.json` in your repo root so teammates get it through version control. Use `--scope local` (the default) to keep it to yourself in this project, or `--scope user` to make it available in all your projects.
- `supabase` is the name you'll see in `/mcp` and `claude mcp list`.

The resulting `.mcp.json` looks like this:

```json
{
  "mcpServers": {
    "supabase": {
      "type": "http",
      "url": "https://mcp.supabase.com/mcp?project_ref=YOUR_PROJECT_REF&read_only=true"
    }
  }
}
```

You can also write that file by hand instead of running the command. Claude Code asks each person to approve project-scoped servers from `.mcp.json` the first time they load.

## Step 2: scope it with URL parameters

The Supabase server takes its security settings from query parameters on the URL. These are the three that matter:

| Parameter | What it does |
| --- | --- |
| `project_ref=...` | Limits the server to a single project. Without it, the server can reach every project your account can. |
| `read_only=true` | Runs all SQL as a read-only Postgres user. |
| `features=database,docs` | Enables only the listed tool groups. |

Parameters combine with `&`. Supabase's own example is `?project_ref=abc123&read_only=true`.

Our default for a new team is all three:

```
https://mcp.supabase.com/mcp?project_ref=YOUR_PROJECT_REF&read_only=true&features=database,docs
```

Supabase groups its tools into areas such as database, debugging, development, Edge Functions, account management, docs, branching, and storage (storage is off by default). Check the docs for the exact identifiers before you widen the `features` list.

## Step 3: authenticate

Start Claude Code in the repo and run `/mcp`. Select `supabase` and follow the browser prompts to sign in and pick the organization. Supabase uses OAuth with dynamic client registration, so you don't need a personal access token for this.

To sign in from your shell instead, run `claude mcp login supabase`. To sign out, use "Clear authentication" in `/mcp` or run `claude mcp logout supabase`.

## Step 4: verify the connection

From your shell:

```bash
claude mcp list           # supabase should be listed as connected
claude mcp get supabase   # shows the URL, scope, and status
```

Inside Claude Code, ask a question only your database can answer:

```
> What tables are in the public schema of this project?
```

Then test the read-only setting on purpose:

```
> Create a table called mcp_write_test with a single id column.
```

With `read_only=true`, that should fail. If it succeeds, your URL is missing the parameter. Fix it before going further, and drop the test table.

## Step 5: useful read patterns

This article uses a simple `tasks` table to keep examples concrete:

```sql
CREATE TABLE tasks (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES auth.users(id),
    title       TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'pending',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Questions that work well:

```
> How many tasks were created in the last 7 days?
> Are there users with more than 50 tasks?
> What's the average age of tasks in pending status?
> Which tables in public don't have row-level security enabled?
```

Three habits make these better:

**Aggregate before showing detail.** Ask "how many?" before "list all." Reading a thousand rows into context to count them wastes tokens and time.

**Anchor on schema.** Start a session with "what tables are in this project?" The assistant writes better SQL once it has seen the schema.

**Check the SQL.** Claude Code shows each tool call before it runs. Read the query. It's the fastest way to catch a wrong join.

## Step 6: row-level security still matters

Row-level security protects your application's users from each other. It's the right default for every Supabase table, AI or not:

```sql
ALTER TABLE tasks ENABLE ROW LEVEL SECURITY;

CREATE POLICY "users see own tasks"
  ON tasks FOR SELECT
  TO authenticated
  USING (user_id = auth.uid());

CREATE POLICY "users insert own tasks"
  ON tasks FOR INSERT
  TO authenticated
  WITH CHECK (user_id = auth.uid());
```

Be clear about what it doesn't do. The MCP server acts on your project through your Supabase account, not as one of your app's signed-in users, so don't count on your RLS policies to limit what the assistant can read. The controls that limit the MCP server are the ones in Step 2: one project, read-only SQL, a narrow feature list, and a non-production project.

## Step 7: writes and migrations

When you need writes, do them on a development project or a branch, never by flipping production to read-write.

1. Point a separate server entry (or a separate repo checkout) at the dev project without `read_only=true`.
2. Ask the assistant to draft the migration as a file in `supabase/migrations/`.
3. Review it for the usual problems: missing `IF NOT EXISTS`, no rollback plan, long locks on big tables.
4. Apply it yourself with the Supabase CLI or your normal deploy pipeline.

The assistant drafts; a person runs the command that changes the data. Claude Code also asks before every tool call, so read each one before you approve it.

## CI and headless setups

OAuth needs a browser. For CI, Supabase documents passing a personal access token as a header instead. In `.mcp.json` that looks like:

```json
{
  "mcpServers": {
    "supabase": {
      "type": "http",
      "url": "https://mcp.supabase.com/mcp?project_ref=${SUPABASE_PROJECT_REF}&read_only=true",
      "headers": {
        "Authorization": "Bearer ${SUPABASE_ACCESS_TOKEN}"
      }
    }
  }
}
```

Claude Code expands the variables from the environment. Set `SUPABASE_ACCESS_TOKEN` and `SUPABASE_PROJECT_REF` as CI secrets, never in the file. Grant the token only what the enabled tools need.

## Local development

If you run Supabase locally with the CLI, the local stack serves an MCP endpoint at `http://localhost:54321/mcp`:

```bash
claude mcp add --transport http supabase-local http://localhost:54321/mcp
```

It's a good place to let the assistant experiment, because nothing there is real data.

## Troubleshooting

- **`supabase` shows as failed or needing authentication.** Run `/mcp`, select it, and authenticate again. If the browser step loops, run `claude mcp logout supabase` and then `claude mcp login supabase`.
- **The command fails or the URL gets cut off.** You probably didn't quote the URL, so the shell split it at `&`. Wrap it in double quotes.
- **The server can see the wrong project, or every project.** Add `project_ref` to the URL and restart the session.
- **Writes succeed when they shouldn't.** `read_only=true` is missing or misspelled. Check with `claude mcp get supabase`.
- **Tools you expected are missing.** Your `features` list is excluding them. Add the group, or remove the parameter to see the full set.
- **The project-scoped server never loads.** You may have declined it at the approval prompt. Run `claude mcp reset-project-choices` and start Claude Code again.
- **You still have an old local config.** Earlier guides, including a previous version of this one, used an npm package with keys in environment variables. Remove that entry with `claude mcp remove` and use the hosted server.

## Security notes

Supabase's docs are direct about the main risk: prompt injection. Data in your tables could contain text that tries to steer the assistant. Their guidance, which we follow:

- Use read-only mode for anything unattended.
- Scope the server to a single project.
- Enable only the feature groups you need.
- Connect a production project only when the task needs production evidence.
- Review tool calls and their output before acting on them.

## FAQ

### How do I add the Supabase MCP server to Claude Code?

Run `claude mcp add --scope project --transport http supabase "https://mcp.supabase.com/mcp"`, start Claude Code, run `/mcp`, and sign in to Supabase. Add `?project_ref=...&read_only=true` to the URL to scope it.

### How do I connect Supabase to Claude Code without a personal access token?

Use the hosted server with OAuth, as above. Supabase only needs a personal access token for manual setups such as CI.

### How do I make the Supabase MCP server read-only?

Add `read_only=true` to the server URL. Supabase then runs all queries as a read-only Postgres user.

### Can I install the Supabase MCP server for every project on my machine?

Yes. Use `--scope user` instead of `--scope project`. You'll usually want to leave out `project_ref` in that case, which means the server can reach every project your account can, so keep `read_only=true`.

### Does the Supabase MCP server respect row-level security?

Don't rely on it. The server acts through your Supabase account, not as an app user. Use the URL parameters to limit it.

### Does the same setup work with Codex?

Yes, the server is a standard remote MCP server. The config syntax differs per client; Supabase's docs list them.
